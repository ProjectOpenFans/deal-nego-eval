凡事皆可打分The Grading Pipeline, End to End

本框架回答一个问题:我们的技能层(skill harness)能否让一个 LLM 在"硬的、吃判断力的、非标准"交易上,成为实质上更强的 dealmaker —— 也就是 Dealhouse 真正服务的那类局。做法很直接:同一批 case,把 harness 关掉(clean)和开启(on)各跑一遍,量它抬升了多少。

回合上限round_cap = 12
指标M1 – M12
判定层次门槛 → 结果 → 质量
信号 · The Signal
quality(on) − quality(clean)
一个 case 只有在 clean 非平凡(裸模型没能直接通吃) 且 on 能把它抬起来 时才算有区分度。两臂都顶格(太易)或都崩(无解)的 case,一律弃用。
STEP 01construct 造 Case 把难度写进 v0:双方 profile、底线、资源集、ZOPA 结构、五档锚。
STEP 02rollout 跑对局 Agent(A 座)对阵 counterparty-sim(B 座),逐轮谈判 ≤ 12 轮。
STEP 03extract 结构抽取 把每轮自由文本抽成结构化 Deal,供确定性指标读取。
STEP 04grade 打分 M1–M12 先过门槛(合不合法),再打质量(有多好)。
STEP 05verdict 判定 V3 门槛 ∧ 结果 = 是否成立;质量按 V3 归零规则装配。
STEP 06aggregate 聚合报告 多次运行汇总成 CaseReport,读出 clean→on 的抬升。
01

数据构造 · Case-Bank Construction

Difficulty is authored, not improvised.

一条 case 就是一份 v0(交易配置)。难度不是"对手嘴硬"造出来的,而是被写死在 v0 的客观设定里——一旦写定,不管哪个 sim、哪次运行,ZOPA 就那么难找、底线就那么苛刻、真需求就藏那么深。

评估单元:一整场谈判对局

每条 case 把一个谈判场景编码成一个 v0 对象:两方参与者——我们的 agent(代表 A 座) 与一个 counterparty 模拟器(扮演 B 座)——各自带 public profile 与 private 约束(reservation 底线、deal-breaker 雷区、真实利益、可动用资源),外加一份作者写定的 ground-truth ZOPA 结构 与一套 五档质量锚(T0–T4)。一场 episode = agent 与 sim 逐轮谈判(至多 round_cap = 12 轮),直到 sim 接受(settled)、走人(walk_away),或撞上回合上限(round_cap)。

核心原则:难度写在 v0,sim 只是小腿

sim 只负责把 v0 里对手的姿态和松口条件翻译成对话行为——它执行难度,不制造难度。据此,每条 case 都要过同一把标尺:

诊断标尺 · The Softening Test
"把 sim 换温和一点,难度还在吗?"

在 → v0 够硬,case 健康。  不在(sim 一软 case 就塌) → 难度错误地压在了 sim 的演技上,v0 没写死,必须返工。

三条正交难度轴,全部写进 v0

难度沿三条互相正交的轴构造。经验法则:一条有意义的 hard case,至少要把两条轴推到"强"。单轴 case 会塌(模型直接就解了);而把 person-hard 推到 frontier(一个客观上根本请不动的对手),是唯一能可靠难住强模型的一轴。

ZOPA 坐在非显然的维度上;简单结构无解(一把现金买断只买到一个空壳);解必须重构交易的性质/方向,而不是换个资源类型。

两条铁律(quick-test 的血泪教训)

Authoring Rule #1

解药和真问题必须藏起来

委托方的解药资源与真问题,必须写在 private 或只能从情境推断——绝不能进 public_profile 让 agent 白读到。一旦答案能直接读到,就没有诊断可做,难度当场塌掉。

  • 反例 C6:"临终关怀专业"写进 public profile → 三模型全 brilliant,难度塌。
Authoring Rule #2

ceiling = 0 只用于纯 cash-trap

把买方现金上限设成 0(掏任何钱都算 fail),只有在委托方本就不该掏钱(掏钱就打烂自己的牌)时才对。对于买方本该付钱的收购/交易型 case,0 上限会误杀正解——该用一个真实上限,让 M6 judge 去抓坏结构。

  • 误伤 C9:收购型,2M 是合理养老结清,却被 ceiling=0 判死 → 已返工为 2.5M。

02

对局执行 · Episode Rollout

The turn loop that produces the transcript.

orchestrator 驱动一场对局:agent 坐 A 座,共享的 counterparty-sim 坐 B 座,逐轮交替,直到 sim 接受、走人或撞上回合上限,产出一份 EpisodeOutput(final_deal + 完整 transcript + process 轨迹)。

orchestrator · run_episode()for r in 1 … round_cap
// 每一轮: 1 a_text = agent.play_turn(history) // A 座发言(被测模型) 2 a_offer = extractor.extract_turn(a_text, prev) // 自由文本 → 结构化 Deal 3 sim_turn = sim.respond(turns, r) // B 座:ACCEPT / COUNTER / WALK 4 if sim_turn.action == "ACCEPT" → terminal="settled"; break if sim_turn.action == "WALK" → terminal="walk_away"; break → 未触发终止且跑满 → terminal="round_cap" final_deal = extractor.extract_final(turns, accepted_offer, status) process = { skills_used, tool_calls, trace, extract_fallbacks, warnings }
Roles & Providers

被测模型 vs. 固定中立层

agent(A 座)= 被测模型;aux = 一个固定中立的模型,同时承担 sim、offer 抽取器、以及 M2/M6/M11/M12 的 judge。换被测模型时只动 agent,aux 保持不变,再 diff 两份 CaseReport。

  • Judge(打分器): Qwen 3.7-max,temperature 0。
  • 被测 agent: DeepSeek-v4-pro · GLM-5.2(本地)· StepFun。
  • 前沿模型(Claude / GPT)留到 case 库与 harness 冻结后的下一轮。
Two Arms

clean 与 on,量抬升

每条 case 都跑两臂:clean = 裸模型,无 harness;on = 模型 + 我们的技能层(deal-diagnosis、interest-discovery、term-reframing …)。

信号就是那道差:quality(on) − quality(clean)。M11 / M12 这两个过程指标只在 on 臂记录——agent 读取了哪些 skill,就是它的诊断/路径信号。

结构抽取器:自由文本 → 结构化 Deal

broker 吐的是散文,但确定性指标(M3/M4/M5/M9/M10)需要结构化报价。抽取器把每轮发言里真实明确提出的条款抽成一个 Deal,并做四件事保证可信:

① 资源吸附  snap

in_kind.resource 与 obligations.maps_to_resource 必须取自本 case 的资源清单 id;抽出的自由名字会被吸附回最接近的合法 id。

② 沿用上一版  carry-forward

未在本轮明确出现的字段沿用上一版。特例:deadline 不从 v0 占位词("近期")继承——否则 M2 会看到一个凭空捏造的期限。

③ 多方案消歧  disambiguate

一轮里摆出多个并列方案(方案一/方案二、括号备选)时,只抽被主推/被对方接受的那一个;被 pass 掉的方案独有条款绝不混入。sim 用自然语言接受时,还会结合接受话术重新定位它到底选了哪个方案。

④ 事后体检  sanity

非阻塞地 flag 高频抽取错误:成交现金从未在对话里出现过(疑似抽取假象)、资源落在清单外、同一 resource 出现多条(疑似并列方案混入)——挂 warning 供审阅,不让 judge 悄悄吸收。

03

打分 · Grading Everything, M1–M12

Gate first, then optimize. Quality never gates; gates never score.

打分是一个分层的"先设闸、再优化"设计:先过硬性通过/不通过的门槛(这笔 deal 到底合不合法?),再打一个分档的质量(它有多好?)。质量永远不当闸用,门槛永远不打分。

Stage 1 · 确定性闸

做了非线性动作吗?

由代码判:agent 是否自己第一个把一个新的非现金维度(in-kind 资源 / 带资源的义务)摆上桌,或在 doomed case 上正确走人?被动接住对方提出的东西不算。没动作 → 直接 floor,不叫 judge——把主分离做成确定性的、稳定的、与模型无关的。

Stage 2 · judge 定档

在锚之间放到哪一档?

只有过了闸才叫 judge。judge 拿本 case 的 T0–T4 锚,把这次运行放进对应档位。当前 R4/R5 采用锁定的五档 rubric;早期 M6 曾用 floor/acceptable/goldman 三档 + "above-Goldman 冻结封顶"的谱系。judge 一律 temperature 0。

锚举例 · R5C1 "粉丝 × 中腰博主"(cash-trap + interest-hard)

难点命门:表面"掏钱支持"掩盖"人设正在崩"的真问题,而解药藏在委托方自己表面无关的专业能力(数据分析)里。  T0 floor:被"打赏/买课/坑位费"带跑,只在掏钱这条轴打转。  T2 sound:看穿真问题是人设崩、用专业能力换共创。  T3 sharp:不依赖博主承认在崩,用专业视角把"掉的是哪批老粉、怎么立回人设"讲到对方无法反驳。  T4 brilliant:地位反转——从"又一个想打赏的散户"反转成"博主的诊断顾问/共创合伙人"。

04

判定装配 · Verdict Assembly (V3)

The heart of the grading — and the piece most worth scrutinizing.

门槛干净 → 结果成立 → 质量装配。质量(M6)的归零规则(当前版本"V3")是最近影响最大的一处改动,也是最值得第二意见的一处。

gates_pass = M1 ∧ M2 ∧ M3 ∧ M4 # 过程是否干净 outcome = M5 # 一笔合法 deal 是否成立(成交 + 现金没破上限) case_pass = gates_pass ∧ outcome quality = M6 档(0–4),按下方 V3 规则装配
V3 质量归零规则 · quality zeroing
分支 Aif NOT gates_pass
quality = 0

泄了底线 / 越权许诺 / 结构不良——不算数,无论谈得多漂亮。门槛(M1–M4)硬归零,不看 judge。

分支 Belif M5 == cash_over_cap
quality = 0

破了现金上限(为"赢"而掏钱/收钱,而正解本是非现金)——这是一笔坏的成交 deal。确定性地硬归零,不信 judge:judge 会被漂亮的操作骗到给破线的局打高分。

分支 C · elsegates clean &
not_settled 或已成交
quality = M6

保留 judge 打的档。包括"回合用尽但仍在建设性推进"的长路径正解——真僵局本来就会被 judge 打成 floor,而一场强但未签字的谈判保住它挣来的档。

为什么这条规则重要:M5 的两种失败,天差地别

cash_over_cap→ 硬归零
一笔坏的成交 deal

agent 破了现金上限——比如在一个正解为非现金的 case 上掏钱去"赢"。这种我们确定性地归零,不交给 judge,因为 judge 会被花哨的操作骗到——实测 R5C2 on 臂上,judge 给一个掏了 2000 现金的破线局打了 sharp(3)。破线是确定性的,就确定性地罚。

not_settled→ 保留 judge 档
仍在建设性推进的长路径

回合用尽时谈判还在建设性推进(硬 case 的正解常是长路径:诊断 → 建信任 → 锁定下一步,在回合上限内还没签字)。这种不归零,让 judge 的档立住:真僵局/无动作本来就被 judge 打成 floor,而一场真正强但未签字的谈判保住它挣来的档。

V3 修的是什么 · The harness-inversion artifact

硬 case 上的正解常是长路径(诊断→建信任→锁下一步,回合内未签)。一个天真的"必须成交"闸会把这些正解砸成 0,反而让 harness 看起来比那个草草签下一笔坏 deal 的裸模型还差。V3 把这个反转修好了。M5(成交率)仍作为独立指标单独记录——它只是不再给质量归零。

05

聚合与报告 · Aggregate

Many runs collapse into one comparable report.

每次运行写一份 EvaluationResult(metrics + verdict)。跑很多次后,按 case 聚合成一份 CaseReport——最终读出的,是同一批 case 在 clean 与 on 两臂之间的抬升。

per-runEvaluationResult
{ case_id, run_id, config: { skills, agent_profile, mode }, metrics: { M1 … M12 }, // 每条的原始判分 verdict: { gates_pass, outcome_pass, case_pass, quality // V3 装配后 } }
aggregateCaseReport
{ case_id, runs, pass_rate, // case_pass 比例 gate_fail_breakdown: { // 各门槛各挂几次 M1, M2, M3, M4 }, quality_mean, // M6 平均(档位建议按档汇报) logs: { rounds, concessions, settlement } }
汇报口径

M6 的 tier 是主输出,应按每档的比例汇报,而非取平均(数值 0–4 仅为向后兼容 verdict.quality 与分布报告保留)。最终结论就是那一句:同一批 case,on 相对 clean 抬升了多少档。
